# AI Engineer Learning Roadmap

Personal project: learn AI/agent engineering hands-on by building each phase locally, then applying it at work.

**New here, or revising?** Read `LEARNING_GUIDE.md` first - the simple step-by-step version, with the flow of each phase and a table of every problem/change/result. This file is the detailed log.

## Machine specs
**Current (from 2026-09-30):** MacBook, Apple M1 Max, 32GB unified memory - models up to ~30B at Q4 run 100% on GPU.

Original (Phases 1-8a):
- CPU: i7-8750H (6C/12T)
- RAM: 16GB
- GPU: GTX 1050 Ti (4GB VRAM)
- Free disk: ~286GB
- Constrained/quantized setup — Ollama offloads a few layers to GPU, leans on CPU/RAM for the rest.

## Model picks
**Current default (M1 Max):** `qwen3-coder:30b` (mixture-of-experts, ~18.6GB, ~3B active per token - fast), `NUM_CTX=32768`, set in `phase5-rag/.env`. Also tested `qwen3.5:27b` - no accuracy gain on the eval, ~80x slower (dense + thinking on by default). See `phase8-framework/FRAMEWORK_COMPARISON_NOTES.md`.

Original picks (Windows laptop):
1. `qwen2.5-coder:7b-instruct-q4_K_M` — best default, ~4.7GB, usable speed
2. `qwen2.5-coder:3b-instruct` — fast fallback if 7B is sluggish
3. Skip 14B+ — VRAM/RAM combo would make it painfully slow

- **Phase 5.5 — Combined agent (RAG as a tool)** ✅ done (`phase5-rag/agent.js`, `phase5-rag/tools.js`)
  Merged the Phase 3 agent pattern with Phase 5's retrieval: one agent, one model, multiple tools — `list_files`, `read_file`, `get_current_time`, plus a new `search_company_docs` tool that wraps the embed+pgvector-search logic from `query.js`. The model itself decides per-question whether to call `search_company_docs` (company/internal questions) or just answer from its own knowledge (general questions) — no manual routing/classification step needed. This is the "agentic RAG" pattern.
  - Tested: "What is our rollback process?" → correctly called `search_company_docs`, answered from the doc
  - Tested: "What is the capital of France?" → answered from its own knowledge, skipped doc search
  - Note: small quantized 7B model is a bit noisy about tool choice (e.g. redundant extra calls) but still lands on the right tool and right answer — expected at this model size, not a bug
  - Run with: `node agent.js "your question"`
  - Purpose: gives Phase 6 one clean backend endpoint (`ask(question) → answer`) to wrap in a UI, instead of the UI having to decide RAG-vs-agent itself

- **Phase 5.6 — Hybrid search** ✅ done (2026-09-26, `phase5-rag/schema.sql`, `phase5-rag/tools.js`, `phase5-rag/agent.js`, `phase6-ui/server/agent.js`, `phase5-rag/docs/equipment.md`, `phase7-reliability/eval.js`)
  Real limitation found and proved live (2026-09-22): pure vector search struggles to distinguish similar-looking exact codes/IDs (e.g. equipment model numbers). A made-up code scored nearly as close as the real one - both comfortably under `RELEVANCE_THRESHOLD = 0.5`, meaning the system would confidently answer about the wrong equipment. Committed a permanent test doc (`docs/equipment.md`, "Equipment Model XJ-2200... calibration every 90 days") so this is a repeatable regression case, not just a one-off live demo.
  - **Schema**: added a generated `content_tsv tsvector` column (`GENERATED ALWAYS AS (to_tsvector('english', content)) STORED`) + GIN index to `doc_chunks`, applied live via `docker exec ... psql < schema.sql` against the running container (backfilled existing rows automatically, no data loss).
  - **What actually shipped, in two legs**:
    1. A keyword/full-text search leg (`websearch_to_tsquery`) merged with vector search via Reciprocal Rank Fusion, so chunks strong in exact wording can surface alongside chunks strong in semantic similarity.
    2. An identifier-mismatch check: if the question names a code-shaped token (regex `[A-Za-z]{1,6}-?\d{2,6}`) and vector search would call a chunk "relevant," but that literal identifier doesn't appear anywhere in that chunk's content, flag `identifierMismatch` and answer "I don't have information about that identifier" instead of blending in the wrong doc - this is the piece that actually fixes the proven bug.
  - **First attempt at identifierMismatch failed, and why**: tried basing the mismatch check on the keyword-search leg itself (`keywordRows.length === 0`) - but `websearch_to_tsquery` ANDs every term in the query, including ordinary words. The real query "calibration schedule for XJ-2200" against a doc that only says "calibration" (no literal "schedule") failed the AND and returned zero keyword rows even for the CORRECT code, flagging every query as a mismatch - a false positive that would've made the fix worse than the bug (verified live: agent answered "I don't have information" even for XJ-2200). Fixed by decoupling the mismatch check from the keyword leg entirely: a direct case-insensitive substring check of the identifier against the vector-relevant chunk's content, independent of how the rest of the question is phrased. Retested both the real and fake code afterward - both correct.
  - **A second, subtler bug found via advisor review before shipping**: the relevance gate (`isRelevant`, `bestDistance`) in both `agent.js` files was reading off the merged/display array, not the raw vector rows. A chunk found ONLY by keyword search has no `distance` field, so `undefined < RELEVANCE_THRESHOLD` would silently evaluate false and drop exactly the chunk hybrid search exists to rescue - invisible at this project's 2-chunk corpus (vector search with `TOP_K=4` always returns every chunk, so a keyword-only row was structurally impossible today) but a real latent bug the moment `docs/` grows past 4 chunks. Fixed by attaching explicit `bestVectorDistance`/`keywordHit` fields (computed from `vectorRows`/`keywordRows` directly) to the returned array, and gating on those instead of the merged content. Reran the eval suite after this fix specifically to confirm it changed nothing observable today (7/7, same as before) - it only fixes behavior at a corpus size not yet reached.
  - **Honest limitation, not chased further**: the keyword/RRF leg is wired in and indexed, but with `websearch_to_tsquery`'s AND semantics it rarely actually contributes at this project's corpus size and phrasing (it returned zero rows even for the project's own headline "correct code" query) - the identifier substring check is what closes the proven failure, not the RRF merge itself. If the keyword leg needs to pull more weight later (larger corpus, more exact-match-dependent questions), switching to OR semantics (`to_tsquery` with `|`) is the knob to try - not done now.
  - **Verified live**: through `phase5-rag/agent.js` (CLI) AND through `phase6-ui/server/agent.js`'s `runAgent` directly (the actual function the browser UI calls) - "What is the calibration schedule for XJ-2200?" correctly answers "every 90 days"; the identical question with "XJ-9999" correctly answers "I don't have information about that specific identifier" instead of blending in the real doc's 90-day figure.
  - **Eval suite**: added 2 new regression cases (`phase7-reliability/eval.js`) - correct code must still answer from the doc, wrong code must NOT mention "2200" or "90 days". Full suite: 7/7 passing (5 pre-existing + 2 new), confirming no regression on the existing cases while adding permanent coverage for this bug.

- **Phase 6.5 — Multi-turn memory** ✅ done (`phase6-ui/server/server.js`, `agent.js`, `web/src/App.jsx`)
  Gap found while testing Phase 6: every question was independent - no memory of prior turns, so natural follow-ups ("what did I just ask about?") failed. Added session-based conversation memory, a standard baseline pattern (not the full production version - see caveats below):
  - Frontend generates a `sessionId` (`crypto.randomUUID()`, persisted in `localStorage`) and sends it with every request; a "New chat" button clears it and starts a fresh session
  - Server keeps an in-memory `Map<sessionId, history>` and passes prior turns into `runAgent(question, history, callbacks)`
  - Only canonical user/assistant turns are stored across requests - the tool_call/tool messages from inside a turn are scratch work and are NOT persisted, so history doesn't balloon with every past doc-search payload
  - History is windowed to the last 10 turns (20 messages) per session to bound context growth on the local model
  - **Production caveats (deliberately not implemented, noted for later):** in-memory Map is lost on server restart and doesn't work across multiple server instances - real production needs Redis/a database keyed by sessionId; windowing just drops old turns rather than summarizing them, which a more advanced system would do instead
  - Verified live in browser: asked about rollback process, then "What did I just ask you about?" → correctly answered "our rollback process"; clicked "New chat", asked the same follow-up again → correctly had no memory of it, confirming the session reset actually works

- **Phase 6.6 — Redis-backed sessions (fixing the multi-instance gap)** ✅ done (`phase6-ui/docker-compose.yml`, `phase6-ui/server/sessionStore.js`, `server.js`)
  Fixed the multi-instance caveat flagged in Phase 6.5, and proved the bug was real before fixing it:
  - Added `redis:7-alpine` via `phase6-ui/docker-compose.yml` (port 6379), `phase6-ui/server/sessionStore.js` wraps `getHistory`/`appendTurn`/`clearSession` using the `redis` npm client, with a 24h TTL per session key (`session:<sessionId>`)
  - `server.js` now calls the async Redis-backed store instead of an in-process `Map`
  - **Reproduced the bug first:** ran two server instances (ports 3001 and 3002, via `PORT=3002 node server.js`) with the OLD in-memory Map code. Same `sessionId`, asked Instance A a question, then asked Instance A "what did I just ask you about?" (correct: remembered) - then asked the SAME follow-up with the SAME sessionId to Instance B instead → it had no idea, proving in-process memory can't be shared across instances
  - **Reran after the Redis fix:** same two-instance setup, same test - Instance B (which never saw that session) correctly answered "You just asked me about our rollback process," confirming both instances now share state through Redis
  - Key lesson: a load balancer routes requests to whichever instance is free, with no awareness of "sessions" - so a real multi-instance deployment needs either sticky sessions (fragile) or shared external state (Redis/DB) - this is exactly why Redis is the near-universal choice for chat session storage in production
  - Flagged but not yet done: our Ollama calls don't set `options.num_ctx`, so the model's 32,768-token architecture max (`ollama show qwen2.5-coder:7b-instruct-q4_K_M`) may not be the context window actually in effect at runtime - conversation history + retrieved doc chunks could silently exceed it and get truncated with no error. Worth fixing explicitly later.

- **Phase 6.7 — Explicit context window + live token usage in the UI** ✅ done (`phase6-ui/server/agent.js`, `server.js`, `web/src/App.jsx`, `phase5-rag/agent.js`)
  Fixed the num_ctx gap flagged in Phase 6.6, and made context usage visible instead of invisible:
  - `agent.js` now sets `options.num_ctx: 8192` explicitly on every Ollama call (`NUM_CTX` constant) - a deliberate middle ground for this machine (16GB RAM, 4GB VRAM): comfortably fits RAG context + conversation history without the memory/latency cost of the model's full 32k max
  - Confirmed via `ollama show qwen2.5-coder:7b-instruct-q4_K_M` (32768 architecture max) and a raw API test that Ollama really does return usable counters: `prompt_eval_count` (tokens read for that call's context) and `eval_count` (tokens generated)
  - `runAgent` now returns `{ answer, usage }` where `usage = { promptTokens, completionTokens, totalTokens, contextWindow, remainingTokens }`, computed from the final (non-tool-call) turn
  - `server.js` sends a `usage` SSE event after the answer finishes streaming
  - `App.jsx` renders it under each assistant reply: a small progress bar + "664 / 8192 tokens used (7528 remaining)" - verified live in the browser
  - Applied the same `num_ctx` fix to `phase5-rag/agent.js` for consistency
  - Note: `promptTokens`/`completionTokens` reflect only the LAST model call in a turn (i.e. after any tool calls) - this is the number that matters for "how full is the context window right now," but it's not a running total of every call made during that turn's tool loop

- **Phase 6.8 — Always-retrieve RAG (fixing hallucination on skipped searches)** ✅ done (`phase6-ui/server/agent.js`, `phase5-rag/agent.js`)
  Found via live testing that the model sometimes skipped calling `search_company_docs` entirely and hallucinated a plausible-but-wrong answer instead - e.g. asked "when does the on-call rotation hand off?" and confidently answered "10:00 PM UTC" when the real doc says "every Monday at 10am." Tried the "advisory" fixes first, then the structural one:
  - **Tried first (partial improvement only):** `temperature: 0` (was `0.2`) and a much stricter system prompt ("You MUST call search_company_docs... even if discussed earlier"). Reduced but did NOT eliminate the skip - reproduced it again afterward with a genuinely new company question following an earlier tool call in the same session. Lesson: prompt wording is advisory, never a hard guarantee, no matter how forcefully worded.
  - **Actual fix - changed the architecture:** `search_company_docs` is no longer a model-chosen tool. It now runs unconditionally on every question (cheap: one embed call + a pgvector lookup) before the model ever sees the question, with results baked directly into the system prompt. This is "classic RAG" (always retrieve, model decides how to use it) rather than "agentic RAG" (model decides whether to retrieve) - the right call for a narrow single-domain assistant like this one, where retrieval is far cheaper than generation, vs. the hybrid-router pattern used in large multi-tool systems to save cost on clearly out-of-domain queries.
  - Removed `list_files`/`read_file` from this agent's available tools entirely (`AGENT_TOOL_DEFS` filter) - they're Phase 3 leftovers with no real use here, and kept causing a specific failure: the model "verifying" the already-injected doc excerpts by trying to read the source file, which always failed (wrong path) and derailed the answer into a confused non-response ("I don't know if they don't contain the answer"). No prompt wording fully suppressed this; removing the tool did.
  - Retested the exact original failure (on-call question) after the fix → now correctly answers "every Monday at 10am." Retested a repeated question and a general-knowledge question in the same session → both still correct, general knowledge still ignores the irrelevant injected doc excerpt.
  - Tool-call events (`tool_call`/`tool_result` SSE) are still emitted for the automatic retrieval, so the UI's live "search happening" indicator still works exactly as before - only WHEN it fires changed (always, not model-decided), not the UI contract
  - Remaining known cosmetic noise (not a correctness bug): the model still occasionally calls a harmless extra tool (an invented tool name, or a pointless `get_current_time`) alongside the correct answer - small-quantized-model looseness, doesn't affect the final answer's correctness anymore

- **Phase 6.9 — Context-limit warnings** ✅ done (`phase6-ui/server/agent.js`, `web/src/App.jsx`, `phase5-rag/agent.js`)
  Ollama gives no signal when a request approaches/exceeds `num_ctx` - proved this earlier by loading a session with ~80,000 chars of synthetic history and asking a real question: no error, `promptTokens` came back at 8158/8192 (Ollama silently dropped older turns to fit), and the request took ~29s vs. the usual ~5-10s. Since the model/API won't warn us, added our own threshold-based warning computed from the usage numbers we do get:
  - `contextWarning(usage)` in `agent.js`: ≥75% of `contextWindow` used → `warningLevel: "warning"`, ≥95% → `"critical"`, each with a human-readable `warningMessage`. Attached to the `usage` object returned by `runAgent` (and the max-turns fallback path too)
  - `App.jsx` renders a colored banner under the token-usage bar when `warningLevel` is set (amber for warning, red for critical), e.g. "⚠️ Approaching the context limit - older conversation history will start getting dropped soon."
  - Verified live end-to-end: reloaded the same ~8k-token synthetic session through the real SSE path (not just curl) - backend correctly sent `warningLevel` in the `usage` event, and the browser correctly rendered the amber warning banner at 7596/8192 tokens (92.7% used)
  - Same logic ported to the `phase5-rag/agent.js` CLI as a `console.log` warning at the same thresholds, for consistency
  - This only warns - it does not prevent truncation or start summarizing/trimming automatically. A further improvement (not done) would be proactively trimming/summarizing history server-side before hitting Ollama, rather than just telling the user after the fact.

  Found a real gap: Redis had the full conversation, but the UI showed a blank chat on every page load/refresh - `messages` only ever lived in React state, never restored from the backend. Fixed that plus a full visual redesign:
  - `sessionStore.js`: added `saveUsage`/`getUsage` (separate Redis key `session:<id>:usage`) so the last-known token usage can be restored too, not just the message history
  - `server.js`: new `GET /api/chat/session/:sessionId` returns `{ history, usage }`; `stream` endpoint now also calls `saveUsage` after each turn
  - `web/src/useChatSession.js`: extracted all chat state into a custom hook using `useReducer` (actions: `LOAD`, `ASK_START`, `TOOL_CALL`, `TOOL_RESULT`, `ANSWER_CHUNK`, `USAGE`, `DONE`, `ERROR`, `RESET`) instead of ad-hoc `setMessages` callbacks in the component - cleaner state management, and `historyToMessages()` converts Redis's plain `{role, content}` turns back into display bubbles on load (no tool-call detail or per-message usage for restored history, since that's scratch work that was never persisted - only the session's last-known usage attaches to the newest restored assistant message)
  - `web/src/TokenRing.jsx`: new circular SVG progress ring in the header showing % of context window used, colored blue/amber/red matching the existing warning thresholds - replaces having to read the small text bar to gauge usage
  - `web/src/App.jsx`: full visual redesign - card layout with shadow, gradient page background, avatar-tagged chat bubbles (user right-aligned blue, assistant left-aligned gray), tool calls now render as small pill badges (⏳ calling / ✓ done) instead of plain text lines, typing-dots animation while waiting, spinner in the Send button while busy, auto-scroll to newest message
  - `web/src/index.css`: replaced the default Vite template CSS (which had a fixed 1126px `#root` width and huge default `h1` sizing that fought the new card layout) with a minimal reset + the two CSS `@keyframes` (spinner, typing dots) inline styles can't define
  - Verified live: asked a question, refreshed the page - full conversation AND the token ring's percentage both restored correctly with zero new requests; "New chat" correctly resets both back to empty/"—"
  - Also fixed a real reliability bug this session's Docker exploration surfaced: `sessionStore.js` had no `'error'` listener on the Redis client, so `docker stop phase6-ui-redis-1` mid-request crashed the ENTIRE Node process (Node's default behavior for an unhandled EventEmitter `'error'` event), not just that one request - reproduced first (stopped Redis, confirmed the whole backend died), then fixed by attaching `client.on("error", ...)` and wrapping every exported function (`getHistory`/`appendTurn`/`saveUsage`/`getUsage`/`clearSession`) in try/catch that degrades gracefully (e.g. `getHistory` returns `[]` on failure instead of throwing) rather than crashing. Retested the identical scenario afterward - server survived, kept answering questions (just without memory) while Redis was down, and fully recovered (including memory) once Redis came back, via the redis client's built-in automatic reconnect.

- **Phase 7 — Reliability/extensibility** ✅ done (`phase7-reliability/`)
  Started with eval tests deliberately first (before logging/retries/config-swapping): they're the safety net Phase 8's framework comparison needs, and they immediately proved their value by catching three real regressions in the existing agent that manual testing had missed.
  - `phase7-reliability/eval.js` - 5 regression test cases against `runAgent` directly (no HTTP), each with `mustContain` substring assertions; run with `npm run eval`. Cases are drawn from real bugs found earlier this project (the Phase 6.8 hallucination, the temp-0 skip-and-repeat case, general-knowledge-must-not-be-derailed, out-of-domain-must-say-don't-know)
  - **Bug 1 found**: "What is the capital of France?" started failing with a garbled non-answer ("I don't know if they don't contain the answer") - the old system prompt's two conditional branches (company-relevant vs. general-knowledge) were confusing the small model into blending both instructions together into nonsense.
  - **Fix attempt 1 (partial)**: restructured the prompt as an explicit numbered Step 1 classification ("is this a company question?"). Fixed the garbling, but introduced a NEW failure: the model then over-applied "I don't know" to the France question too, incorrectly classifying it as company-related.
  - **Bug 2's real fix (structural, not prompt wording)**: moved the relevant/irrelevant decision out of the prompt entirely and into code, using the `distance` number pgvector already returns. Measured empirically: real company questions score ~0.36-0.44 distance, unrelated questions ~0.67-0.68 - a wide, safe gap. `RELEVANCE_THRESHOLD = 0.5` in `agent.js` now decides this in code; the LLM is never asked to classify relevance itself. Same lesson as Phase 6.8 all over again: asking a small model to make a judgment call is inherently unreliable, deciding structurally in code isn't.
  - **Bug 3 found** (after fixing bug 2): the "rollback process" question - previously reliable - started failing too, with a plain "I don't know." even though the correct excerpt was right there in the prompt. Root cause: the prompt's exact wording `respond with exactly: "I don't know."` embeds that literal phrase as quoted text, which the small model (at `temperature: 0`, greedy decoding) was latching onto as an anchor and echoing regardless of whether it actually applied. Fixed by rewording to avoid ever quoting the fallback phrase verbatim.
  - **Bug 4 found** (after fixing bug 3): "capital of France" started failing again, differently - looped through all `MAX_TURNS` calling `get_current_time` repeatedly (traced live: 5 back-to-back pointless calls, then gave up with no final answer) instead of just answering. Root cause: once it was the ONLY tool still available to the model, it seemingly defaulted to calling it when uncertain rather than just answering directly. Fixed by dropping `get_current_time` from `AGENT_TOOL_DEFS` entirely (it never served a real purpose in this agent anyway) - same fix pattern as the earlier `read_file`/`list_files` removal in Phase 6.8.
  - **End state**: 5/5 eval cases pass, verified live through the real SSE path too. Bonus: since the model now gets NO tool schema at all for general questions, `promptTokens` for "capital of France" dropped from ~500+ to 36, and per-question latency dropped roughly 3-6x (no wasted turns considering tools it can't use).
  - Key meta-lesson: every one of these 4 bugs was found because the eval suite re-ran the SAME test questions after each change - something manual interactive testing kept missing because we only ever tested going forward, never re-checked earlier "solved" cases after a later change. This is exactly why an eval suite matters, not just as a nice-to-have.
  - **Logging/tracing** ✅ done (`phase5-rag/tracer.js`, used by both `phase6-ui/server/agent.js` and `phase5-rag/agent.js`)
    - `logTrace(trace)` appends one JSON line per agent run to `phase5-rag/logs/traces.jsonl` - the hand-built version of what a tool like Langfuse gives you. Each line: `timestamp`, `question`, `isRelevant`, `bestDistance` (the actual pgvector score that drove the relevance decision - directly answers "why did it answer this way"), `toolCalls` (every tool called, in order), `answer`, `usage`, `latencyMs`, `turns`
    - Wrapped in try/catch so a logging failure can never break a real request - same "nice-to-have can't take down the must-have" principle as `sessionStore.js`'s Redis error handling
    - Verified live: sent a company question and a general question through the real backend, confirmed both traces written correctly - the France question's trace correctly shows `isRelevant:false`, `bestDistance:0.674`, low token usage, low latency, giving a genuine after-the-fact audit trail for "why did the agent answer this way" without re-running anything
  - **Retries** ✅ done (`phase5-rag/retry.js`, used by `phase5-rag/tools.js`'s `embed()` and both `agent.js`'s `callModel()`)
    - `withRetry(fn, options)`: exponential backoff (500ms, 1000ms, 2000ms by default), only retries genuinely transient failures - network-level errors (`fetch` throwing a `TypeError`, connection resets) and 5xx/429 HTTP responses. Deliberately does NOT retry 4xx errors (e.g. a real bad request) since those fail identically every time - retrying them would just waste time
    - Verified the mechanism directly with an isolated unit test (no network involved): a function that fails twice then succeeds → correctly retried with the right backoff timing and succeeded on attempt 3; a function that fails with a 400 → correctly failed immediately on attempt 1, no wasted retry
