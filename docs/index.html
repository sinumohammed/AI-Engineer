Phases 1 to 10 · local models with Ollama, then free cloud services

AI Engineer Learning Guide

Fifteen steps from the first local model call to a multi-agent chat app working over a real 241-page handbook, then running on the internet on free services. Each step adds one capability, and each one was proved to work before the next began.

Source code on GitHub

Key words

Model (LLM)
The program that turns text into text. Here qwen3-coder:30b, run by Ollama.
Messages
The list sent to the model: system instructions, then user and assistant turns.
System prompt
The instructions at the top of the messages. Guidance, never a guarantee.
Token
A piece of a word. Models read and write tokens, and limits are counted in them.
Context window
The most tokens a model can read in one call. Past it, older text is dropped without warning.
Temperature
Randomness. At 0 the same question gives the same answer, which tests need.
Tool
A function in your code that the model can ask to be run.
Agent
A loop: call the model, run any tool it asks for, give it the result, repeat.
Embedding
A list of numbers that stands for the meaning of a text. Similar meaning, close numbers.
RAG
Find relevant text first, then let the model answer from it.
Hallucination
The model stating something false as if it were true.
Eval
An automated test for an AI system: fixed questions with checks on the answers.
Trace
A saved record of one run: what was found, what was called, what was answered.
Structured output
Forcing the model's reply to match a JSON schema.
Router (supervisor)
An agent whose only job is deciding which other agent answers.
Specialist
An agent with one narrow job and its own prompt.
Chunk
A small piece of a document, about 500 characters, embedded and searched on its own.
Relevance judging
A model reads the search results and keeps only the ones that really answer the question. Also called reranking.
Citation
The answer marks where each fact came from, "12 weeks [1]", and lists section [1] under it, so you can check it.
hit@k, MRR
Search scores. hit@10: the right chunk is in the top 10. MRR: the average of 1 / its rank; 1.0 means always first.
Groq
A hosted service that runs open models very fast, with a free tier.
Free tier limits
Caps per minute and per day, on requests, tokens or texts, that a free plan allows.
Quantization (q8)
Storing a model's numbers with fewer bits: smaller and faster, slightly less exact.
Serverless function
Code the host starts when a request arrives and stops when idle. The first request after a stop is slower: a cold start.
Fallback
A second option used automatically when the first fails, like a smaller model when the bigger one's daily limit is used up.
Access code, CORS
A shared code the API requires, and the browser rule that only the app's own website may call the API.

Step by step

Step 1

A model on the laptop

Phase 1

Have a model running locally, with no cloud service.

Built
Installed Ollama and pulled a model.
Learned
Ollama starts at login and listens on localhost:11434. It holds no model in memory until the first request, loads it on demand (about 21 GB for the current one) and unloads it 5 minutes after the last request.
Try it
ollama list
ollama ps
Step 2

Call the model from code

Phase 2

Talk to the model from Node.js, with no framework in between.

Built
phase2-node-ollama/chat.js waits for the whole answer. chat-stream.js prints it as it arrives.
Flow
Your code posts { model, messages } to Ollama's /api/chat and gets a message back.
Learned
The messages array, system prompts, temperature and streaming. The model has no memory: it only knows what is in the messages you send.
Try it
cd phase2-node-ollama
npm run chat
npm run chat:stream
Step 3

An agent

Phase 3

Let the model do things, not only talk.

Built
phase3-node-agent/agent.js is the loop. tools.js holds list_files, read_file and get_current_time.
Learned
Small models sometimes write the tool request as plain text instead of in the proper field, so the agent has a fallback that reads it from the text.
Try it
cd phase3-node-agent
npm run agent
Step 4

MCP

Phase 4

Move the tools out of the agent, behind a standard interface.

Built
phase4-mcp/mcp-server.js offers the tools. client-agent.js is the same loop, now asking the server what exists.
Learned
Any MCP server can be plugged into the same agent. Claude Code uses this interface for its own tools.
Try it
cd phase4-mcp
npm run agent
Step 5

RAG for company documents

Phase 5

Answer questions from your own documents, not only from what the model remembers.

Built
phase5-rag/ingest.js prepares the documents, query.js answers a question, Postgres with pgvector runs in Docker, sample docs live in phase5-rag/docs/.
Learned
Answer quality depends on finding the right chunk. If search returns the wrong text, the model answers from the wrong text.
Try it
cd phase5-rag
docker compose up -d
npm run ingest
node query.js "What is our rollback process?"
Step 6

Combined agent

Phase 5.5

One agent that answers company questions and general questions.

Built
phase5-rag/agent.js and tools.js. Document search became a tool called search_company_docs.
Flow
The model reads the question and decides: search the documents, or answer directly.
Learned
This "model decides" design is called agentic RAG. It worked in testing and later turned out to be the source of a hallucination bug, fixed in step 8.
Try it
cd phase5-rag
node --env-file=.env agent.js "What is our rollback process?"
Step 7

Chat UI

Phase 6

Use the agent from a browser.

Built
phase6-ui/server/ is an Express API. phase6-ui/web/ is a React app.
Flow
The browser opens /api/chat/stream?q=… and the server pushes events back as they happen: tool_call, tool_result, answer_chunk, done.
Learned
Server-Sent Events let the server report progress while the agent is still working.
Try it
cd phase6-ui
./start.sh
Then open http://localhost:5173.
Step 8

Making the chat app real

Phases 6.5 to 6.11

Seven small iterations, each fixing one gap found by using the app.

PhaseGap foundWhat changed
6.5Every question was independent, so follow-ups failedThe server keeps the conversation per session and sends the last 10 turns with each question
6.6Memory lived inside one server processHistory moved to Redis, so several server copies share it
6.7The context window size was never setnum_ctx is set explicitly and the UI shows tokens used
6.8The model sometimes skipped the search and made up an answerSearch runs on every question, in code
6.9Ollama gives no warning when the context is fullThe app computes its own warning at 75% and 95%
6.10A refresh showed an empty chat, and Redis going down crashed the serverThe UI restores history on load, and Redis errors are handled
6.11Turns older than 10 were forgottenOld turns are folded into a short running summary

Phase 6.8 is the one to remember. A stricter prompt reduced the problem and did not remove it. Removing the choice did.

Step 9

Reliability

Phase 7

Know when a change breaks something.

Built
  • phase7-reliability/eval.js: fixed questions with checks on the answers.
  • phase5-rag/tracer.js: one saved record per run.
  • phase5-rag/retry.js: retry temporary failures with a growing delay.
  • phase5-rag/config.js and .env: model, context size and thresholds in one place.
Flow
For each test question, run the agent and check that the answer contains certain text and avoids other text.
Learned
The eval found 4 bugs that manual testing had missed, because it re-ran old questions after every change. One fix moved the "is this document relevant?" decision out of the prompt and into code, using the search distance number.
Try it
cd phase7-reliability
node --env-file=../phase5-rag/.env eval.js
Step 10

Hybrid search

Phase 5.6

Stop search confusing codes that look alike.

Problem
Asking about a made-up code XJ-9999 returned the real XJ-2200 document, because the two look almost the same to vector search.
Built
Keyword search next to vector search, plus a check: if the question names a code and that exact code is not in the document found, the agent says it has no information.
Learned
Vector search is good at meaning and bad at exact identifiers.
Try it
Ask the chat app about XJ-2200 (it answers "every 90 days") and XJ-9999 (it refuses).
Step 11

A framework

Phase 8a

Rebuild the same agent with LangChain and measure the difference.

VersionDesignResult
AAlways search in code, then one model callSame score as hand-written, less code
BThe model decides whether to call the search tool0/7 on the small model, 7/7 on the bigger one after fixes
Built
phase8-framework/agent-a.js and agent-b.js, run through the same eval as the hand-written agent.
Learned
  • Version B's first 0/7 was mostly the small model's unreliable tool calling.
  • Version B passed its system prompt under the wrong option name and LangChain silently ignored it. A silently ignored option is worse than an error.
  • gemma3:4b, a 4 GB model, matches the 21 GB model on Version A and the hand-written agent. It cannot run Version B, because it does not support tools.
Try it
cd phase7-reliability
AGENT_MODULE=../phase8-framework/agent-a.js node --env-file=../phase5-rag/.env eval.js
Step 12

Multi-agent

Phase 8b

Split the work across several agents and see what that costs.

FileJob
supervisor.jsThe hand-written flow
supervisor-graph.jsThe same flow written with LangGraph
routing.jsRouter prompt and rules, shared by both
specialists.jsThe three specialists, shared by both
llm.jsThe hand-written call to Ollama
eval.jsRouting tests, two-part tests, history tests
Learned
  • The router chooses by structured output, not tool calling, so it works on models without tool support.
  • Splitting into agents created a bug the single agent did not have. "How are rollbacks done?" went to the coding specialist, because the router knew what each specialist is for and not what the documents contain. The fix was to search first and show the router what was found.
  • LangGraph gave the same results with more code. It pays off for flows with loops, pauses or per-conversation memory, which this one does not have.
Try it
cd phase8b-multi-agent
npm run ask -- "What is our rollback process, and how do I list git tags?"
Step 13

Multi-agent in the chat UI

Phase 8c

Use the supervisor from the chat app and compare it with the single agent on the same question.

Built
  • A "Single agent / Multi-agent" switch in the header.
  • A row above each answer showing which specialist answered, with timings and the router's reason.
  • A dropdown to pick a specialist yourself: Auto, Company docs, Coding, General.
Learned
Three problems were found only by using the app. Each was fixed and added to the eval.

Step 14

Real documents at real size

Phase 9

Test search on a real corpus. Everything before used two made-up files, 2 chunks, where search cannot miss.

Built
  • The public TTS Handbook (241 pages, public domain) in phase5-rag/docs/handbook/, and a git-ignored docs-private/ folder for confidential documents.
  • phase9-real-docs/retrieval-eval.js: a test of search alone, with no model call. It checks whether the passage that answers each question reaches the agent.
StepChangeEffect
9.1Load the handbook: 2 chunks become 2,340Paraphrased questions: answer in the top 4 only 3/10. The 0.5 threshold called 5/8 off-topic questions relevant.
9.2Clean the text: strip front matter, template tags, link addresses, HTMLTop result correct for 14/20 direct questions, was 7/20
9.3Cut at headings, label each chunk "Page > Section", 500 characters, nomic task prefixes17/20 top result; private docs 4/4, was 2/4
9.4The model judges relevance instead of a distance thresholdOff-topic wrongly relevant 0/8, was 7/8
9.6Citations: answers name the document section each fact came from37/37 document answers cite a source
Learned
  • At 2 chunks search could not fail, so the earlier tests could not see search problems. A test of search on its own found them.
  • A threshold tuned on a tiny corpus breaks when the corpus grows: off-topic questions moved from a distance of 0.67 to as close as 0.30.
  • What goes into a chunk, clean text and its section, mattered more than the chunk size.
  • The prompt-versus-code lesson came back: a stronger router instruction did not stop it sending "Who is eligible for FMLA?" to the general specialist, and a rule in code did.
Try it
cd phase9-real-docs
npm run eval
npm run eval:citations
In the chat app, ask "How much paid parental leave do I get?" and look at the Sources under the answer.

The lessons that keep repeating

Several of these were first learned on 2 sample documents and had to be qualified once Phase 9 loaded a real handbook. The wording below is the current version; the table after the list shows what changed.

  1. A prompt is advice when it asks the model to follow a rule. A stricter prompt failed where a change in code worked: always-search (6.8), hiding tagged answers (8c), and in Phase 9 a router instruction that did not stop "Who is eligible for FMLA?" going to the general specialist. Exception found in 9.4: a focused question with a structured answer ("which of these excerpts answer the question?") did respond to better wording, from 1 to 0 false positives out of 8. Asking a model to obey a policy against its own preference failed; asking it to judge one specific thing worked. Measure either way. In Phase 10, "use the short name" was ignored; giving the model a smaller job and doing the rest in code worked.
  2. Let code decide when it has a reliable signal, and re-check the signal when the data changes. Relevance by vector distance (Phase 7) was a reliable code rule at 2 chunks and failed at 4,288. It was replaced by the model's judgement (9.4), which in turn feeds a code rule (9.6). In Phase 10 the same rule was extended to each part of a two-part question: both gpt-oss models split it correctly but guessed the wrong specialist for one part, and a per-part document check in code fixed it on every model.
  3. Remove the wrong option instead of forbidding it. Unused tools were deleted, not discouraged.
  4. Prove the bug before fixing it. Each fix started by reproducing the failure, so the fix could be measured.
  5. Re-run old tests after every change. Most bugs were regressions: a fix for one question broke another.
  6. Tests can be wrong too. Correct answers failed on wording, a test set with only easy two-part questions hid a routing bug, and a test assumed the documents say nothing about backups, which stopped being true.
  7. Using the app finds what tests miss. All three problems in step 13 came from clicking around, then became permanent tests.
  8. More agents means more places to fail. Multi-agent added routing mistakes and memory leaking between agents, and doubled the model calls.
  9. Test the parts, not only the final answer. A retrieval eval with no model call found problems that answer tests could not see, and showed which step to fix.
  10. A result measured on toy data is a guess about real data. The 0.5 threshold, fixed 800-character chunks and "the keyword search rarely helps" were all right for 2 chunks and wrong for 4,288.
  11. Bigger is not always needed, so far. For "read this text and answer", a 4 GB model matched a 21 GB one, and size mattered when the model had to choose and call tools. On the handbook, in Phase 10, gpt-oss-20b judged search results as well as gpt-oss-120b.
  12. Different models fail differently. A lenient model can pass by luck: qwen kept a vague follow-up working with four loose matches; strict gpt-oss exposed the weakness, and an old router bug with it.
  13. Free tiers have limits you only find by hitting them. Per minute, per day, per request or per text, different for every service: Gemini counts each embedded text, 1,000 a day; Groq counts tokens per day per model. The limits shaped the design.
  14. Make silent failures loud. A wrong database password looked like "no documents found", a framework ignored a misspelt option, and mixed embedding models would give plausible wrong results. Each now fails with a clear message.
